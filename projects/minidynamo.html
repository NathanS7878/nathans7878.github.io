MiniDynamo

A KV-cache-aware LLM inference router — a distributed Rust and Python serving system modeled on NVIDIA Dynamo.

RustTokioaxumPythonFastAPIPrometheus

~90% cache reuse (vs 69% round-robin) · ~38% lower p50 time-to-first-token · higher throughput, pooled over repeated runs.

The problem

When many users hit an LLM server with prompts that share a common prefix — a system prompt, a document, a conversation history — the KV cache for that prefix can be reused instead of recomputed. But only if the request lands on the worker that already has it.

A round-robin load balancer scatters those requests across the pool and throws the cache away. The work of recomputing a prefix that another machine already holds is pure waste, and it shows up directly as time-to-first-token.

How it works

  • An async Rust frontend (axum on Tokio) exposes an OpenAI-compatible streaming API.
  • Each incoming prompt is tokenized and hashed into prefix-dependent blocks, so two prompts that share an opening share their leading block hashes.
  • The router maintains a mirror of which worker holds which cached prefix blocks and scores each worker as overlap − λ·load — the longest matching prefix wins unless that worker is already busy, so a popular prefix can't pile every request onto one machine.
  • Requests are proxied to a pool of Python (FastAPI) workers — each with a real LRU cache of KV blocks and a simulated model (prefill cost per uncached block, decode cost per token) — with streaming passthrough, so tokens reach the client as they are produced rather than after the full completion.

What I measured

A concurrent benchmark harness compares routing policies head to head on the same workload, so the only variable is the routing decision.

What I got wrong

The router's cache mirror could drift from reality. When a client disconnected early, the worker's actual cache state and the router's model of it diverged, so subsequent routing decisions were made on stale information — the router didn't know about cache that a worker really held.

Prometheus instrumentation is what surfaced it: the cache-hit rate read 0% because the mirror was only updated when a response stream finished — and the benchmark client disconnects right after the first token, so the update never ran. Fixed by updating the mirror at dispatch time (the moment a worker receives the request), not at stream completion, so an early disconnect can't leave it stale.

Limitations

  • The workers are simulated. They keep a real KV-block cache, but model compute with timed sleeps, so the benchmark tests routing decisions under a cost model rather than a real model's latency. A real backend (llama.cpp, or nano-infer) is the next step.
  • Single-node worker pool, with no cross-node cache sharing. Scaling past one machine would need a distributed view of cache residency, which is a materially harder problem than the one solved here.
  • The prefix-block hash assumes deterministic tokenization. A tokenizer change invalidates the mirror's assumptions.
  • Benchmarks are on one hardware configuration. The ~38% figure is what this workload did on this machine, not a general claim about cache-aware routing. Under a saturating workload the gain shrinks toward zero as the load-aware term correctly trades cache affinity for balance.
